# Ledgy (nome provvisorio)

App personale per registrare le spese, pensata per sostituire Wallet by BudgetBakers. Gira come web app, Android e iPhone. Il proprietario vive a Bali: spende in IDR e altre valute del Sud-Est asiatico, ragiona in EUR.

Funzioni scelte, decisioni e note tecniche: [docs/funzioni.md](docs/funzioni.md).

## Regole di lavoro

- Rispondi in italiano.
- Lavora con un solo agente. Usa subagenti o più agenti solo quando fanno risparmiare uso del piano; altrimenti procedi da solo, anche se più lentamente.
- Non generare mai APK o IPA senza un permesso esplicito del proprietario. Le build mobili partono solo da un workflow manuale (`workflow_dispatch`), mai in automatico.
- In GitHub Actions ogni `actions/upload-artifact` usa `retention-days: 1`.
- APK e IPA, quando ci saranno, si pubblicano su **DMReleases**, come le altre app del proprietario (chiedere i dettagli prima della prima build).
- Repository pulito: niente build, file generati, screenshot o file temporanei nel repo.

## Comandi

- `npm test`: tutti i test. `npm run test:unit` solo la logica condivisa; `npm run test:integration` avvia il vero Worker (wrangler dev, D1 locale nuovo, tassi fissi) sulla porta 8799 e prova l'API.
- `npm run test:e2e`: prova dell'interfaccia con Playwright su un Worker già avviato (vedi l'intestazione di `tests/e2e/smoke.mjs`).
- `npm run typecheck`: controllo dei tipi di web app e Worker.
- `npm run build`: compila la web app in `dist/`.
- Sviluppo in locale: `npm run db:migrate:local`, poi `npm run build && npx wrangler dev` e si crea un account dalla schermata di accesso.
- `python3 tools/shortcut/build_shortcut.py`: rigenera il comando iPhone non firmato in `tools/shortcut/out/` (ignorata da git). La versione firmata con HubSign, servita dall'app a `/ledgy.shortcut`, è `public/ledgy.shortcut`: se cambia lo script, va rifirmata e sostituita.
- Pubblicazione: [docs/DEPLOY.md](docs/DEPLOY.md).

## Struttura

- `shared/`: logica pura usata da Worker, web app e test (importi, lettura notifiche, regole, doppioni). `keywords.ts`: parole chiave in molte lingue e marche → categoria (vince la frase più lunga); `brands.ts` aggiunge migliaia di negozi e marche (Bali e Sud-Est asiatico, Emirati, Italia, Europa…). Tabella frase → categoria costruita una volta all'avvio: il costo dipende dal testo, non dal numero di voci, quindi se ne possono aggiungere senza pesare (evitare parole comuni: c'è un test).
- `worker/`: API su Hono e D1. `capture.ts` è il percorso notifica → movimento.
- `src/`: web app React. Navigazione con l'hash (`#/movimenti`, `#/m/<id>`).
- `migrations/`: schema D1. Importi interi in millesimi; segno negativo = uscita. `occurred_at` tiene il fuso del telefono, `occurred_utc` serve per ordinare e confrontare.

## Architettura decisa

- Frontend: React + Capacitor, un solo codice per web (PWA), Android e iOS. Parti native piccole in Kotlin (lettore notifiche) e Swift (App Intents, estensione Condividi).
- Backend: Cloudflare, sul piano gratuito del proprietario. Un solo Worker `ledgy` con static assets serve web app e API; D1 come database; R2 per le foto (quando servirà); Cron Trigger per le pulizie notturne. Niente Supabase.
- Limiti da rispettare: 10 ms di CPU per richiesta e 5 milioni di righe lette al giorno su D1 (superato una volta: blocca tutto fino a mezzanotte UTC). Nelle query le date si confrontano direttamente su `occurred_at` (`>= ?`, `< date(?, '+1 day')`), mai con `substr`, così si usano gli indici della migrazione 0012 (utente+data, utente+negozio senza maiuscole, conto); niente join della tabella movimenti con sé stessa (i doppioni recenti si cercano in `findDuplicates`). Il pianificatore a volte sceglie l'indice sbagliato (es. quello per ordinare): sulle query calde si forza con `INDEXED BY`. Saldi dei conti e saldo totale da `account_totals` (per utente, conto e valuta, tenuta dai trigger della migrazione 0012), mai sommando tutto lo storico. Per misurare: `npx wrangler dev --var D1_ROWS:1` e l'intestazione `x-d1-rows` di ogni risposta (`worker/rows.ts`); una Home con 5.000 movimenti legge circa 3.000 righe. Tutto ciò che scorre molti dati (export, import, regole sullo storico, import da Wallet) lavora a pagine guidate dal browser.
- Account come Multifolio: si usa subito senza account come *ospite* (riga di `users` senza email, creata da `POST /api/guest`); poi si crea un account (email e password, impronta PBKDF2) o si entra in uno esistente scegliendo cosa fare dei dati dell'ospite (`worker/guest.ts`: unisci, usa solo l'account, sostituisci; per la registrazione porta i dati o inizia vuoto), con finestra di conferma. Ogni riga ha `user_id`; categorie, regole e conti iniziali hanno id con suffisso (`cat_food~usr_…`). Recupero con codice di recupero (24 caratteri), niente email né servizi esterni. Il Cron toglie gli ospiti vuoti dopo 7 giorni e quelli senza sessioni.
- Ordine: prima web app + server, con la cattura via automazioni del telefono (Comandi su iPhone, MacroDroid su Android). Poi le app native.
- Niente cifratura end-to-end: il server deve leggere il testo delle notifiche per creare le spese.
- Categoria di un movimento (`classify` in `worker/transactions.ts`): regole dell'utente → ultima spesa confermata dello stesso negozio (le correzioni vincono) → regole predefinite "morbide" (`definition.soft`, in `worker/seed.ts`: viaggiatori dalla versione 3, correzioni e nomi puliti delle catene dalla 4; un account riceve solo quelle delle versioni che non aveva) → parole chiave → AI in background (`waitUntil`) → "da rivedere".
- AI (`worker/ai.ts`, come PackSnap): chiavi Gemini e NanoGPT per account in `ai_settings`, mai restituite intere all'app; sono nel backup (riga `ai` delle impostazioni, scelta del proprietario) e passano dall'ospite all'account se l'account non ne ha. Prima Gemini con la ricerca Google; se la ricerca Google non va (la chiave gratuita ha limiti più bassi per la ricerca) si richiede senza ricerca; con il limite raggiunto (429) si salta per il tempo suggerito da Gemini (o un'ora) e si usa NanoGPT (modello più economico, `:online` per cercare, senza se non va). `last_error` annota servizio, errore e codice HTTP. L'AI si chiama solo se regole, storico e parole chiave non trovano la categoria, e una volta sola per movimento (`transactions.ai_tries`, scelta del proprietario): se non risponde, il movimento resta "da rivedere"; nessun controllo orario la richiama. Nei test Gemini e NanoGPT sono finti (`AI_ENDPOINTS`, server in `tests/integration/server.ts`).
- Home a schede (`src/pages/Home.tsx`, `HOME_WIDGETS`): accese e ordine in `users.home_layout`, nel backup come le altre impostazioni; le schede sconosciute si scartano. Il periodo (mese, anno, da inizio anno, date) è lo stesso di Statistiche (`src/period.ts`, scelta in `src/PeriodSheet.tsx`). Saldo di tutti i conti = somma di `balance_eur` dei conti (bootstrap, cambio di oggi). Lo stato della cattura sta in Altro, non in Home. Riquadro in alto in due stili (`users.hero_style`, scelta in Personalizza): `compact` (budget compatto, predefinito: speso, quanto resta, barra con la tacca di oggi, quanto al giorno) e `ring` (anello); senza budget mostrano media e previsione con l'invito a impostarlo. Il totale dei conti sta accanto al titolo Conti.
- Pubblicazione automatica: `.github/workflows/pubblica.yml` a ogni push sul branch (test → punto di ripristino → migrazioni → deploy → controllo).
- Categorie predefinite versione 2 (`worker/seed.ts`, `TREE`): gruppi facoltativi (Famiglia, Regali, Animali) creati spenti (`archived = 1`). `upgradeCatalog` porta gli account dalla versione 1 (stile Wallet) alla 2 al primo avvio: le predefinite diventano esattamente quelle nuove, movimenti e regole passano secondo `RETIRED`. Il test con tutte le categorie v1 è in `tests/integration` (`categories-v1.json`).
- Tema: `data-theme` su `<html>` (`light` = mockup, predefinito anche col telefono scuro; `blue`, `dark`, `system`), letto da `public/theme.js` prima del disegno. Valuta di visualizzazione: `eur()` in `src/util.ts` converte i totali in euro al tasso di oggi.
- Importi: `formatMoney` (`shared/money.ts`) scrive "1.234,50 €", "208.500 Rp", "12,00 $" (simbolo dopo, migliaia sempre separate, spazio che non va a capo); `.money` non va mai a capo e `fitSize` (`src/util.ts`) rimpicciolisce i numeri lunghi. Nella lista, un movimento nella valuta di visualizzazione mostra l'importo originale.
- Correzione del saldo (`POST /api/accounts/:id/adjust`): la differenza è un movimento `type 'transfer'`, `source 'adjustment'`: cambia solo il saldo, non conta in statistiche, budget, avvisi (migrazione 0011 ha sistemato quelle vecchie salvate come spese).
- Svuota il bilancio (`POST /api/account/wipe-transactions`, conferma `SVUOTA`): cancella solo movimenti e notifiche ricevute; conti, categorie, regole, carte, impostazioni e chiavi restano. Serve prima dell'import da Wallet.
- Import da Wallet (`worker/wallet.ts`, `shared/wallet.ts`, pagina `src/pages/WalletImport.tsx`): API REST ufficiale di BudgetBakers (serve Wallet Premium), chiave solo nella pagina e mai salvata; Wallet non accetta CORS, quindi passa dal Worker. Prepara (conti, categorie abbinate, etichette, totale; senza filtro di data Wallet dà solo 3 mesi) → crea conti → pagine da 100 (`external_id = wallet:<id>`, niente doppioni, pausa su 429) → saldi uguali a Wallet (convertiti nella valuta del conto di Ledgy e sommati se più conti di Wallet finiscono nello stesso; un conto con lo stesso nome si propone solo se ha la stessa valuta). Nei test un Wallet finto (`tests/integration/wallet-fake.ts`, `WALLET_API`).
- Budget (`worker/budgets.ts`): `category_id = '*'` è il totale (il tetto); i budget di categoria sono ritagli; lo sforamento di una categoria si toglie da "tutto il resto".
- Viaggi (`worker/trips.ts`): luogo e date; `trip_items` aggiunge (`in`) o toglie (`out`) movimenti; le spese restano nelle loro categorie. Filtri dei movimenti in `GET /api/transactions` (q, type, card, label, min/max in millesimi di euro, trip, sum=1 per i totali).
- Spese ricorrenti (`shared/recurring.ts`, `worker/recurring.ts`): proposta solo con stesso negozio, importo entro il 15%, intervallo regolare (settimana, 2 settimane, mese, 2/3/6 mesi, anno: `period` + `every`), almeno 3 volte e ancora attiva; l'utente conferma o scarta, oppure la aggiunge a mano con la prossima data (`last_date`).
- Avvisi, previsione e riepilogo settimanale (`worker/insights.ts`), accesi o spenti in Altro › Funzioni (`users.features`, `FEATURE_DEFAULTS` in `worker/auth.ts`; riepilogo spento di base). Gli avvisi nascosti restano solo sul dispositivo (localStorage).
- Assistente (`worker/assistant.ts`, `src/pages/Assistant.tsx`): domande (il server manda all'AI i dati già sommati, nella valuta di visualizzazione), spese scritte o dettate e foto di scontrini/screenshot → movimenti da confermare. Le foto non si salvano. D1 accetta al massimo 100 parametri per query: liste lunghe a gruppi di 90.
- Il backup include tutte le tabelle dell'account, preferiti e impostazioni compresi: una tabella o impostazione nuova va aggiunta a `worker/backup.ts`, `src/backup.ts`, `worker/guest.ts` e alla pulizia in `worker/index.ts`.
